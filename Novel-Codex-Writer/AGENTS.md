# Novel-Codex-Writer 项目协作规则

本项目不是普通代码项目，而是一个用于多部长篇小说持续创作的 Codex + GPT 写作工作流。所有协作者都必须把它当作“小说生产与记忆管理系统”来使用。

## 总原则

- 第一优先级是保持每一本小说自身的连续性、设定一致性、人物状态一致性和伏笔可追踪。
- 本项目采用作品库结构，不再默认只有一本小说。
- 写章前必须先读取 `小说项目/projects.json`，确认 `activeProjectId` 指向哪一本小说。
- 如果 `activeProjectId` 为空，必须先让用户在网页端新建或选择小说，不要凭空创建正文。
- 不要跨小说读取资料；除非用户明确要求对比多本小说，否则只读取当前小说目录。
- 每章正文必须控制在 2000 字以上、2500 字以下；低于 2000 字不得视为合格章节，高于 2500 字必须压缩后再提交。
- 写章前不要读取全部正文；必须读取目标章之前连续最多五章的正文全文，以磁盘上最新保存内容为准，避免遗漏用户对近期正文的修改。
- 写章前必须先生成或刷新当前小说的 `记忆库/current/本章写作任务书.md`。
- 写章时只使用与本章有关的材料，不把整个作品库一次性塞进上下文。
- 不要开始写正文，除非用户明确要求“写第几章”或“续写第几章”。

## 当前小说路径规则

当前小说目录由下面两步确定：

1. 读取 `小说项目/projects.json`。
2. 使用 `activeProjectId` 拼出当前小说目录：`小说项目/作品/<activeProjectId>/`。

后续所有大纲、正文、记忆库、档案库、审查报告和章节提交，都必须在当前小说目录里操作。

## 每章写作前默认读取范围

常规写章前先运行记忆诊断和任务书脚本。读取脚本选出的完整条目和连续前五章正文，不默认全文加载大纲、current 或更早历史正文：

- `大纲/细纲_第XXX章.md` 中的本章目标、必须变化、不可违背事实和结尾钩子。
- 根据篇纲内“章节范围”自动匹配的 `大纲/第NN篇_*.md` 中与本章有关的规则。
- `记忆库/current/本章写作任务书.md` 中检索出的当前状态和来源 ID。
- 目标章之前连续最多五章的正文全文；不足五章时读取已有全部前章，缺少任一连续前章时停止写作。
- 最近两章的结构化摘要与上一章结尾状态。摘要和 current 继续用于长期状态，但不得代替前五章最新正文。

如果用户修改了近期章节正文，后续写章必须直接读取修改后的文件。正文与旧摘要、旧章末状态冲突时，先向用户报告冲突，以最新正文为准，并在写完新章前修正相关记忆，不能静默使用旧摘要。

如果总纲、章节规划、唯一匹配的篇纲或本章细纲不存在，停止写作并明确报告缺少的文件，不要猜测、回退到固定卷纲或自动虚构细纲。

## 回查规则

- 只有需要核对特定人物、地点、伏笔、设定或事实时，才读取当前小说的 `档案库/`。
- 只有需要确认五章以前的剧情原文时，才继续读取当前小说的更早章节正文。
- 回查时要说明要查什么、为什么查、查到后如何影响本章。
- 不要为了“更保险”而默认读取全部正文。
- 不要读取其他小说的正文、记忆库或档案库来补当前小说。

## current 投影规则

- 当前小说的 `记忆库/current/` 是当前投影，不是历史流水账。
- current 文件只保存当前仍会影响后续创作的信息。
- current 不得无限追加；关闭、过期或矛盾的信息要通过结构化 `memory_patch` 迁移到档案库。
- 更新 current 时必须先运行 `update_memory.py --dry-run`，校验通过后再正式执行。
- Markdown 是事实源；`记忆库/index/memory_index.json` 只是可删除、可重建的检索索引。

## 历史保存位置

每本小说的完整历史保存在自己的项目目录中：

- `正文/`：章节正文原文。
- `章节提交/`：每章提交记录。
- `档案库/`：人物、伏笔、地点、设定、事实的历史档案。
- `记忆库/snapshots/`：只保存篇末压缩摘要和明确的人工基线。

## 每章完成后的必做事项

每章写完后必须在当前小说目录内完成：

1. 保存章节正文到 `正文/`。
2. 生成章节审查报告到 `审查报告/`。
3. 生成章节 commit 文本到 `章节提交/`。
4. 生成 `memory_patch`，说明本章对人物、关系、伏笔、设定、时间线、不可违背事实的影响。
5. 先 dry-run，再使用 `update_memory.py` 根据 `memory_patch` 自动更新 current、档案和索引。
6. 检查章节字数是否在 2000-2500 字之间；不达标时必须先扩写或压缩正文，再生成最终审查和提交记录。

## 压缩归档规则

- 每章在 memory_patch 中保存短摘要和章末状态，不再每 5 章生成 snapshot。
- 只有完整篇纲范围结束时，才使用 `compact_memory.py --range 起始章-结束章` 生成篇末摘要。
- 非篇末范围只做诊断，不归档、不生成 snapshot。
- 压缩不是删除历史；完整历史保留在正文、章节提交和档案库中。

## 网页端删除规则

- 网页端删除小说或 Markdown 文件时，默认移动到 `小说项目/.trash/`。
- 不要手动清空 `.trash/`，除非用户明确要求永久删除。
- 不要把 `.trash/` 当作当前创作资料读取。

## 安全边界

- 不要提交账号、密码、cookie、token、API key、`.env` 或浏览器缓存。
- 不要自动合并 PR 到 main。
- 不要删除分支。
- 不要 force push。
- 高风险操作必须先问用户。
